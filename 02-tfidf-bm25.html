    Від тексту до TF-IDF і BM25

    Як комп'ютер бачить текст, як зробити з нього числа і як побудувати пошук, який досі працює у production у 2026 році.

    Задача пошуку (IR) ділиться на два підходи:

    Full-text / lexical

    За ключовими словами

    За сенсом

    Розділ 1

    Навіщо класичні алгоритми, коли є нейронні мережі?

    Lexical search не помер. Він стоїть під капотом Elasticsearch, OpenSearch, Lucene, Solr, Postgres full-text і майже кожної RAG-системи як перший етап відбору кандидатів.

    01 · Дешево

    Не потрібне тренування

    Немає датасету, немає GPU, немає ручної розмітки. Індекс будується за секунди на CPU.

    02 · Точно

    Досі сильний baseline

    На бенчмарку BEIR BM25 обходить багато нейронних моделей на незнайомих доменах (zero-shot).

    03 · Терміни

    Абревіатури і коди

    Артикул «XR-2200-B» або тікет «PROJ-4821» ембедінг не знає. Точний збіг токена знає завжди.

    04 · Прозоро

    Легко пояснити

    Чому документ у топі? Бо у ньому є ці слова з такою вагою. Кожен доданок скору можна показати.

    05 · Швидко

    Мільйони документів

    Інвертований індекс дає відповідь за мілісекунди. Нейронний пошук потребує окремої векторної БД.

    06 · Гібрид

    Hybrid search

    У production зазвичай поєднують: BM25 відбирає кандидатів за точним збігом, нейронна модель їх перевпорядковує.

    Розділ 2

    Текстові дані: що бачить комп'ютер?

    Для нас текст — це символи, що складаються у слова, речення і сенс. Для комп'ютера текст — це послідовність байтів. Стандарт Unicode присвоює кожному символу номер (code point), а кодування UTF-8 записує цей номер у 1–4 байти.

    Текст як байти

    interactiveВведіть будь-який текст. Спробуйте латиницю, кирилицю, японську і емоджі та порівняйте кількість байтів на символ.
    Питання

    Чому б не працювати з байтами напряму? Комп'ютер їх уже «розуміє».

    Розмиття сенсу

    Байт «0xD0» сам по собі не означає нічого. Він частина літери, яка частина слова. Сигнал розмазаний по кількох позиціях, і статистика по байтах ловить шум, а не зміст.

    Висока розмірність і довжина

    Один символ може займати від 1 до 4 байтів. Кирилиця займає 2 байти на літеру, емоджі 4. Послідовність байтів у 2–4 рази довша за послідовність символів, а комбінацій байтів набагато більше, ніж символів.

    Код із ноутбука: візуалізатор байтів на Python
    def visualize_unicode_bytes(text: str):

    Розділ 3

    Рішення: токенізація

    Токенізація — це перетворення тексту на змістовні одиниці, токени. Мета — стиснути текст у набір блоків, кожен з яких несе частину сенсу.

    Токеном може бути що завгодно: байт, символ, набір символів (subword), слово, словосполучення, речення чи абзац. Формат токена обирає розробник під задачу. Сьогодні токен = слово.

    Розділ 4

    Як представити токени числами?

    Найпростіший спосіб: порахувати, скільки разів кожен токен зустрічається у документі. Це Bag of Words: порядок слів ігноруємо, лишаємо тільки лічильники. Чим частіше слово у документі, тим, імовірно, воно важливіше для нього.

    TF(t,d) = кількість входжень токена t у документі dзагальна кількість токенів у документі d

    Часто TF (Term Frequency) беруть просто як сирий лічильник f(t,d) без ділення. Обидва варіанти називають TF. Це джерело плутанини, і ми до неї повернемось у BM25.

    Розділ 5

    Як врахувати, що слово повторюється у всьому корпусі?

    У матриці вище слово «навчання» є у кожному документі. Воно нічого не «підсвічує»: за ним не можна відрізнити один документ від іншого. Для цього вигадали IDF, Inverse Document Frequency: чим у більшій частці документів зустрічається токен, тим менша його вага.

    IDF(t) = log Ndf(t) = log кількість документів у корпусікількість документів, у яких є токен t

    scikit-learn використовує згладжену версію log((1+N)/(1+df)) + 1. Одиниця у чисельнику і знаменнику захищає від ділення на нуль для нового слова, а +1 гарантує, що слово, яке є у всіх документах, не обнулиться повністю.

    TF-IDF

    Перемножуємо: частота токена у документі з урахуванням його рідкості у корпусі.

    TF-IDF(t,d) = TF(t,d) · IDF(t)

    TF-IDF для нашого корпусу

    liveРахується з документів, які ви ввели у розділі 4. У клітинках: TF-IDF (лічильник). IDF класичний із згладженням +1, як у ноутбуці.

    import math

def idf(n_docs, n_docs_with_token):
    # згладжений варіант: +1, щоб не ділити на нуль для невідомих слів
    return math.log((n_docs + 1) / (n_docs_with_token + 1))

def tf(n_tokens_in_doc, n_token_mentions):
    return n_token_mentions / n_tokens_in_doc

def tf_idf(n_tokens_in_doc, n_token_mentions, n_docs, n_docs_with_token):
    return tf(n_tokens_in_doc, n_token_mentions) * idf(n_docs, n_docs_with_token)

tf_idf(10, 6, 100, 90)      # 0.0626
    Розділ 6

    Як шукати за TF-IDF векторами?

    Маємо векторизований корпус і векторизатор, який робить такий же вектор для нового запиту. Запит і документи тепер точки в одному просторі розмірності «розмір словника». Лишилось порівняти вектори.

    Варіант 1

    Евклідова відстань (L2)

    Відстань між кінцями векторів. Проблема: довгий документ має більший вектор, і відстань росте навіть за однакового набору слів. Немає фіксованого діапазону, важко інтерпретувати.

    Варіант 2

    Косинусна подібність

    Косинус кута між векторами. Ігнорує довжину, дивиться тільки на напрямок. Однаковий набір слів → кут 0 → подібність 1. Жодного спільного слова → кут 90° → подібність 0.

    cos(q,d) = q · d‖q‖ · ‖d‖ = Σ qidi√Σqi² · √Σdi²

    Загалом косинус лежить у [−1, 1]. Але TF-IDF ваги невід'ємні, тому для TF-IDF векторів косинусна подібність завжди у [0, 1]: «протилежних» текстів тут не буває. Є тільки «спільних слів немає» (0) і «набір слів однаковий» (1).

    Пошук по міні-корпусу рецензій

    interactive14 коротких рецензій замість 25 000 з IMDB. Запит проходить той самий векторизатор, документи ранжуються за косинусом. Збіги підсвічено. Спробуйте «scary movie», «boring plot», «great acting».
    from datasets import load_dataset
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np

reviews = load_dataset("imdb")["train"]["text"]            # 25 000 рецензій
vectorizer = TfidfVectorizer()
tfidf_matrix = vectorizer.fit_transform(reviews)           # ~7 с на CPU, словник 74 849 токенів

def tfidf_search(query, top_n=5):
    query_vector = vectorizer.transform([query])           # той самий словник і IDF
    sims = cosine_similarity(query_vector, tfidf_matrix).flatten()
    best = np.argsort(sims)[::-1][:top_n]                  # індекси у порядку спадання
    return [(reviews[i], sims[i]) for i in best]

for text, score in tfidf_search("scary movie"):
    print(f"{score:.4f}  {text[:80]}...")
    Що робить TfidfVectorizer за замовчуванням

    Приводить текст до нижнього регістру, токенізує регулярним виразом (?u)\b\w\w+\b (пунктуація ігнорується, токен — це мінімум 2 літери чи цифри), рахує IDF як log((1+N)/(1+df))+1 і нормалізує кожен вектор документа до одиничної довжини (L2). Через це косинусна подібність зводиться до звичайного скалярного добутку. Стоп-слова, N-грами і уніфікацію акцентів можна ввімкнути параметрами.

    Розділ 7

    Як оцінити якість пошуку без ручної перевірки?

    Тестовий датасет для пошуку має дві частини: корпус документів і набір запитів, до кожного з яких відомий список релевантних документів. Тоді можна порахувати метрики, схожі на метрики класифікації, але тільки для топ-K результатів.

    precision@K = релевантних серед топ-KK recall@K = релевантних серед топ-Kусіх релевантних для запиту F@K = 2 · P·RP+R

    Розділ 8

    Як обробити текст перед TF-IDF і навіщо?

    Кожен унікальний токен — це +1 вимір вектора. Розмітка, регістр, стоп-слова і форми слова роздувають словник і розмивають сигнал. Обробка нижче має накладатися і на корпус, і на запити, інакше вони не зійдуться у одному словнику.

    Розмітка і шум

    HTML, посилання, емоджі

    Зустрічаються по всьому корпусу і не допомагають пошуку. Прибираємо регулярними виразами або BeautifulSoup.

    Регістр

    Hello = HELLO = hello

    Для статистики згадка слова — це вже маячок. Регістр не важливий, тож усе у нижній регістр.

    Стоп-слова

    «і», «але», «the», «is»

    Є у більшості текстів, тому їхній IDF і так близький до нуля. Стоп-словом може бути й доменне слово: назва університету в документах про цей університет.

    Словоформи

    Стемінг vs лематизація

    Стемінг зрізає закінчення за правилами: швидко, але може дати неіснуюче слово («beauti»). Лематизація приводить до словникової форми через морфологію: точніше, але повільніше. Для української стандарт — pymorphy2/pymorphy3.

    Навіть якщо стемер зріже «університет» і «університетський» до неіснуючого «університ», для пошуку це не проблема. Один «токен» тепер позначає два споріднені слова, і документ отримує їхню сукупну вагу.

    import re
from nltk.corpus import stopwords
from nltk.tokenize import word_tokenize
from nltk.stem import PorterStemmer, WordNetLemmatizer
from nltk.util import ngrams

text = "<p>The <b>runners</b> were running through the gardens!</p>"

text = re.sub(r'<.*?>', '', text)                       # 1. прибрати HTML-теги
text = text.lower()                                     # 2. нижній регістр
tokens = word_tokenize(text)                            # 3. токени
stop_words = set(stopwords.words('english'))
tokens = [t for t in tokens if t not in stop_words]     # 4. стоп-слова

stemmer = PorterStemmer()
print([stemmer.stem(t) for t in tokens])                # ['runner', 'run', 'garden', '!']

lemmatizer = WordNetLemmatizer()
print([lemmatizer.lemmatize(t, pos='v') for t in tokens])  # ['runners', 'run', 'gardens', '!']

print(list(ngrams(tokens, 2)))                          # [('runners', 'running'), ('running', 'gardens'), ...]
    Розділ 9

    TF-IDF — це не тільки пошук

    TF-IDF вектор — це звичайний числовий вектор. Його можна передати будь-якій класичній моделі машинного навчання як табличні ознаки.

    Класифікація

    TF-IDF + логістична регресія або LinearSVC. Досі сильний baseline для спаму, тональності, тем.

    Ключові слова

    Топ-N токенів документа за TF-IDF — це його теги, проста сумаризація або визначення теми.

    Кластеризація

    K-Means поверх TF-IDF групує документи за схожим словником.

    Рекомендації

    «Схожі статті»: косинус між TF-IDF векторами документів.

    Автоматичні теги за TF-IDF

    BM25: production-версія лексичного пошуку

    BM25 — це функція ранжування з імовірнісної моделі релевантності. Це дефолт у Lucene, Elasticsearch і OpenSearch. Вона не векторизує документи. Вона напряму рахує оцінку для пари «запит – документ».

    Два недоліки TF-IDF, які виправляє BM25

    Проблема 1

    TF росте лінійно

    У TF-IDF слово, згадане 20 разів, важить у 20 разів більше, ніж згадане один раз. Але 20-та згадка «scary» майже не додає впевненості, що документ про страшне кіно. Потрібне насичення (saturation).

    Проблема 2

    Довгі документи виграють

    З сирими лічильниками довгий документ має більше входжень будь-якого слова просто через довжину. Потрібна нормалізація за довжиною, але керована, а не жорстке ділення на довжину.

    Також класичний TF-IDF не має жодних параметрів для налаштування: він вчить лише словник і IDF. BM25 вводить два параметри, k1 і b.

    Насичення TF: параметр k₁

    interactiveВнесок одного слова у скор залежно від кількості його входжень у документ. Довжина документа дорівнює середній, тому нормалізація тут не діє. k1 зазвичай 1.2–2.0.
    TF-IDF: лінійний внесок f(t,d)BM25: насичується і ніколи не перевищує k1+1

    k1 = 0 перетворює TF на бінарну ознаку «слово є або немає». Великий k1 наближає поведінку до лінійної.

    Нормалізація за довжиною: параметр b

    interactiveТой самий термін з 3 входженнями, але документ різної довжини відносно середньої по корпусу (avgdl). b зазвичай 0.75.

    b = 0: довжина документа не впливає взагалі. b = 1: повна нормалізація, внесок терміна масштабується на |d|/avgdl. Документ довший за середній штрафується, коротший — отримує бонус.

    Формула BM25

    score(q,d) = Σt ∈ q IDF(t) · f(t,d) · (k1 + 1)f(t,d) + k1 · (1 − b + b · |d|avgdl)
    • f(t,d) — сирий лічильник входжень токена у документ. Не частка від довжини. Довжина враховується окремо через b.
    • |d| — довжина документа у токенах, avgdl — середня довжина документа у корпусі.
    • Сума йде по токенах запиту. Документ отримує один скор на запит. Косинус тут не потрібен.
    IDFBM25(t) = log ( N − df(t) + 0.5df(t) + 0.5 + 1 )

    0.5 у чисельнику і знаменнику — це згладжування: воно захищає від ділення на нуль і від log(0). Оригінальна формула Робертсона без «+1» дає від'ємний IDF для слів, що є у понад половині документів. Lucene/Elasticsearch і бібліотека rank_bm25 додають +1 під логарифм, щоб IDF завжди лишався невід'ємним і дуже часте слово просто важило майже нуль, а не віднімало скор.

    Часті непорозуміння щодо BM25

    1. «У формулу BM25 підставляється нормалізований TF = лічильник / довжина». Ні. Підставляється сирий лічильник f(t,d). Якщо підставити частку, довжина документа буде врахована двічі і формула втратить сенс: f стане меншим за 1, і насичення майже не буде працювати.

    2. «BM25 — це два оновлені множники, а далі як у TF-IDF: вектори і косинус». Ні. BM25 не будує вектор документа і не порівнює його з вектором запиту. Це сума внесків тільки тих термінів, що є у запиті. Нормалізації вектора немає, тому скор не обмежений одиницею і не порівнюється між різними запитами.

    3. «0.5 у IDF потрібне лише проти ділення на нуль». Частково. Це ще й згладжування оцінки ймовірності, і саме через нього IDF може стати від'ємним у оригінальній версії. Тому у production додають +1.

    4. «BM25 — це покращений TF-IDF». Це корисна інтуїція, але походження інше: BM25 виведений з імовірнісної моделі релевантності (Probabilistic Relevance Framework), а TF-IDF — евристика з векторної моделі. Збіг структури «щось схоже на TF, помножене на щось схоже на IDF» — це результат, а не відправна точка.

    Реалізація з нуля
    import math
from collections import Counter

class BM25:
    def __init__(self, tokenized_docs, k1=1.2, b=0.75):
        self.k1, self.b = k1, b
        self.docs = tokenized_docs
        self.doc_len = [len(d) for d in tokenized_docs]
        self.avgdl = sum(self.doc_len) / len(tokenized_docs)
        self.tf = [Counter(d) for d in tokenized_docs]           # сирі лічильники f(t, d)
        df = Counter(t for d in tokenized_docs for t in set(d))  # у скількох документах є t
        N = len(tokenized_docs)
        self.idf = {t: math.log((N - n + 0.5) / (n + 0.5) + 1) for t, n in df.items()}

    def score(self, query_tokens, i):
        s = 0.0
        norm = 1 - self.b + self.b * self.doc_len[i] / self.avgdl
        for t in query_tokens:                                   # сума ТІЛЬКИ по термінах запиту
            f = self.tf[i].get(t, 0)
            if f == 0:
                continue
            s += self.idf.get(t, 0) * f * (self.k1 + 1) / (f + self.k1 * norm)
        return s

    def search(self, query_tokens, top_n=5):
        scores = [(self.score(query_tokens, i), i) for i in range(len(self.docs))]
        return sorted(scores, reverse=True)[:top_n]

tokenize = lambda s: s.lower().split()
bm25 = BM25([tokenize(d) for d in docs])
bm25.search(tokenize("scary movie"))

    Підсумок

    Текст → числа

    Байти → токени → лічильники

    Токенізація стискає байти у змістовні одиниці. Bag of Words рахує їх і дає sparse-вектор розмірності словника.

    TF-IDF

    Частота × рідкість

    TF каже, наскільки слово важливе для документа. IDF каже, наскільки воно рідкісне у корпусі. Пошук — косинус між векторами.

    BM25

    Насичення + довжина

    Сирий лічильник із насиченням через k1, нормалізація за довжиною через b, невід'ємний IDF. Сума по термінах запиту, без векторів і косинуса.

    Обробка

    Однаково для корпусу і запиту

    Регістр, стоп-слова, стемінг, N-грами. Один і той самий конвеєр на обох сторонах.

    Перевірте себе

    Слово є у кожному документі корпусу. Який його класичний IDF = log(N/df)?
    log(1) = 0. Слово нічим не допомагає відрізнити документи. В оригінальному BM25 IDF без +1 такий токен був би вже від'ємним.
    Документ B — це документ A, скопійований три рази підряд. Яка косинусна подібність TF-IDF векторів A і B?
    Вектор B — це вектор A, помножений на 3. Напрямок той самий, косинус дорівнює 1. Саме тому косинус кращий за евклідову відстань для текстів різної довжини.
    Що підставляють як TF у формулу BM25?
    Сирий лічильник. Довжина документа входить у формулу окремо через параметр b і відношення |d|/avgdl.
    Що станеться з BM25, якщо задати k₁ = 0?
    При k₁ = 0 дріб дорівнює f·1/(f+0) = 1 для будь-якого f > 0. Лишається тільки сума IDF термінів запиту, що є у документі. Довжину контролює b, а не k₁.
    Чому BM25 не використовує косинусну подібність?
    BM25 — це функція ранжування, а не векторизатор. Внесок мають лише токени запиту, а нормалізація довжини вбудована у сам дріб через b.
